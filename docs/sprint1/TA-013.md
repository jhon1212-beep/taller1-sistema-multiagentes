## Objetivo

Automatizar, en una suite de integración que corre sin red ni base de datos,
los ocho casos del plan de pruebas de TA-003 sobre los componentes reales ya
construidos y el dataset controlado de TA-017. Donde un caso depende de algo
que todavía no existe, la prueba queda **bloqueada con el motivo**; nunca se
marca como aprobada.

## Cómo se realizó

1. **Lectura del plan** (`TA-003.md`): precondición, pasos y esperado de cada
   CP, y qué dependencias ya figuraban como bloqueadas.
2. **Mapeo a componentes reales:** cada CP se asoció al componente que hoy lo
   cubre (tabla anterior) en lugar de simularlo.
3. **Fecha de corte en el dataset (TA-017):** se agregó
   `FuenteEvidenciaDataset(fecha_corte=...)` y `fecha_corte_demo()` para
   consultar el dataset "como estaba" en cada semana.
4. **Casos límite construidos a propósito:** CP-03 usa una fuente con las
   cuatro combinaciones de campos faltantes; CP-06 usa cuatro tareas con el
   escenario 25 % → 50 % del plan; CP-02 inyecta un `RateLimitError`.
5. **Valores calculados a mano** para CP-05: al corte del 29/09 el proyecto 1
   tiene 7 commits y 13 quedan fuera de corte.
6. **Bloqueos explícitos:** seis pruebas `skip` con el texto "BLOQUEADO" y lo
   que falta, que `-rs` imprime como lista de pendientes.

## Limitaciones

- **Un CI verde no equivale a aceptación:** los 6 casos bloqueados son los
  pendientes reales del producto (ver `TA-003.md`).
- Las pruebas usan datos controlados, no integraciones reales; la
  conectividad real se verifica aparte (TA-007, `pruebas-github-por-caso`,
  verificación de HU-004 con Notion).
- I2 se interpreta como % de tareas `Sin empezar` (ver `TA-019.md`).
- CP-08 usa el contrato de autenticación y los servicios; falta el control de
  acceso en las rutas del servidor.
