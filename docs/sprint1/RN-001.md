# RN-001 · Seguridad de secretos

## 1. Registramos los datos del PBI

Para iniciar la actividad, revisamos los datos definidos para **RN-001 · Seguridad de secretos**. Esta tarea busca evitar que credenciales o archivos sensibles queden expuestos dentro del repositorio.

| Campo | Información |
|---|---|
| PBI | RN-001 · Seguridad de secretos |
| Story Points estimados | 0.5 SP |
| Horas estimadas | 2 horas |
| Horas reales | Pendiente de registrar |
| Responsable | Reyes |
| Verificador | Mondragón |

## 2. Revisamos la protección de archivos sensibles

Primero revisamos el archivo `.gitignore` para comprobar que los archivos que pueden contener credenciales no sean incluidos por Git.

Confirmamos que `.env` se encuentra excluido. Además, agregamos la regla `service-account-*.json` para evitar que un archivo de credenciales de una cuenta de servicio pueda subirse accidentalmente.

Para comprobar las reglas utilizamos:

```powershell
git check-ignore -v .env service-account-drive.json
```

Con esta verificación comprobamos qué regla de `.gitignore` protege cada archivo.

**Evidencia:** `RN-001_check_ignore.png`

## 3. Verificamos el archivo `.env.example`

Después revisamos `.env.example`. Este archivo funciona como plantilla para indicar qué variables necesita el proyecto, pero sin almacenar sus valores reales.

Comprobamos que contiene los seis nombres requeridos:

```text
GITHUB_TOKEN=
NOTION_TOKEN=
GOOGLE_SERVICE_ACCOUNT_JSON=
GEMINI_API_KEY=
LANGSMITH_API_KEY=
DATABASE_URL=
```

Así mantenemos documentadas las variables necesarias sin publicar tokens, claves de API u otras credenciales.

## 4. Verificamos la instalación de Gitleaks

Para revisar el historial utilizamos **Gitleaks**. Después de instalarlo, verificamos la versión mediante:

```powershell
gitleaks version
```

La versión utilizada fue **8.30.1**.

## 5. Escaneamos el historial del repositorio

Ejecutamos Gitleaks desde la raíz del repositorio:

```powershell
gitleaks git -v --report-path docs/sprint1/evidencias/RN-001_gitleaks.json
```

El escaneo terminó sin detectar secretos en el historial revisado.

**Evidencia:** `RN-001_gitleaks_repo.png`

## 6. Realizamos una prueba positiva de Gitleaks

También realizamos una prueba fuera del repositorio utilizando un token falso. La intención fue comprobar que el resultado de cero secretos del repositorio no se deba simplemente a que la herramienta no esté funcionando.

En el primer intento, Gitleaks analizó el archivo de prueba, pero mostró:

```text
no leaks found
```

Por ello, no registramos este intento como una detección exitosa. La prueba positiva queda pendiente de repetirse con un patrón de prueba que pueda ser detectado de forma verificable.

**Estado:** Pendiente de completar satisfactoriamente.

## 7. Configuramos los secretos en GitHub Actions

Luego ingresamos a **Settings → Secrets and variables → Actions** y registramos como **Repository secrets**:

- `GEMINI_API_KEY`
- `LANGSMITH_API_KEY`
- `NOTION_TOKEN`

Obtuvimos las credenciales reales desde sus respectivas plataformas y las registramos directamente en GitHub. No colocamos sus valores en el código, en `.env.example` ni en las capturas.

**Evidencia:** `RN-001_actions_secrets.png`

## 9. Cerramos la actividad

Con las verificaciones realizadas cumplimos los tres criterios de aceptación definidos para **RN-001**. Comprobamos que los archivos sensibles están protegidos mediante `.gitignore`, que `.env.example` documenta las variables necesarias sin exponer sus valores y que las credenciales utilizadas por las integraciones están almacenadas como Repository secrets en GitHub.

También escaneamos el historial con Gitleaks 8.30.1 y obtuvimos cero secretos detectados. Dejamos registrada la prueba positiva como pendiente porque el primer patrón falso utilizado no produjo una detección; de esta forma documentamos el resultado obtenido sin presentar como exitosa una prueba que todavía debemos repetir.
