# RN-001 · Seguridad de secretos

## 1. Objetivo

El objetivo de RN-001 es evitar que credenciales, tokens, claves privadas, archivos de configuración sensibles o cadenas de conexión sean almacenados accidentalmente dentro del repositorio.

La verificación considera tres mecanismos principales:

1. Protección de archivos sensibles mediante `.gitignore`.
2. Detección de secretos mediante Gitleaks.
3. Uso de Repository Secrets para las credenciales utilizadas por las integraciones.

Las pruebas realizadas permiten comprobar tanto que el repositorio actual no contiene secretos detectables como que Gitleaks sí responde correctamente ante un patrón controlado.

---

## 2. Reglas de seguridad

| Regla | Aplicación y comprobación |
|---|---|
| No guardar secretos en código ni documentación | Tokens, claves y cadenas de conexión reales se completan únicamente en el entorno local o en el almacén de secretos del servicio que los utilice. |
| Excluir archivos de credenciales | `.gitignore` excluye `.env`, `.env.*`, `service-account-*.json`, `client_secret_*.json`, `credentials.json`, `token.json`, `*.pem` y `*.key`, también en subcarpetas. La exclusión fue comprobada mediante `git check-ignore`. |
| Mantener una plantilla pública | La excepción `!.env.example` permite versionarla. Sus variables sensibles se dejan vacías y no se copian valores del entorno local a esta plantilla. |
| No revelar secretos en evidencias | Se omiten valores de tokens, cabeceras `Authorization`, contraseñas y contenido real de archivos de credenciales en capturas, logs e informes. |
| Usar permisos mínimos | Las integraciones deben utilizar únicamente los permisos necesarios para cumplir su función. El workflow de TA-035 mantiene `contents: read` y sus pruebas actuales no requieren secretos. |
| Revisar antes de publicar | Antes de publicar cambios se revisa el diff y se ejecuta un detector de secretos sobre archivos e historial. `.gitignore` no elimina archivos ya versionados ni detecta secretos incrustados dentro de otros archivos. |
| Responder a una exposición | Ante una exposición se debe revocar o rotar la credencial comprometida, actualizar sus consumidores y coordinar la limpieza del historial. Borrar únicamente el archivo del último commit no invalida un secreto previamente expuesto. |

## 3. Variables requeridas

El archivo:

[`.env.example`](../../.env.example)

incluye los nombres de las variables necesarias, manteniendo vacíos los valores sensibles:

```dotenv
GITHUB_TOKEN=
NOTION_TOKEN=
GOOGLE_SERVICE_ACCOUNT_JSON=
GEMINI_API_KEY=
LANGSMITH_API_KEY=
DATABASE_URL=
```

Se conserva además la configuración adicional requerida para GitHub y OAuth de Google Drive.

`GOOGLE_SERVICE_ACCOUNT_JSON` representa la ruta local del archivo de credenciales cuando se utilice una cuenta de servicio. Su presencia en la plantilla no implica que este método de autenticación ya se encuentre implementado.

El archivo real `.env` no debe ser versionado.

## 4. Verificación de archivos ignorados

Para comprobar que los archivos sensibles están protegidos por `.gitignore`, se realizó una prueba desde la raíz del repositorio.

Se creó temporalmente el archivo:

`service-account-prueba-ignore.json`

mediante:

```powershell
New-Item -ItemType File -Path service-account-prueba-ignore.json
```

Después se ejecutó:

```powershell
git check-ignore -v .env service-account-prueba-ignore.json
```

El resultado confirmó que ambos archivos se encuentran protegidos por las reglas definidas en `.gitignore`.

La salida identificó las reglas correspondientes para:

- `.env`
- `service-account-*.json`

Una vez terminada la verificación, el archivo temporal fue eliminado.

### Evidencia

`docs/sprint1/evidencias/RN-001_check_ignore.png`

### Resultado

**Cumple.**

`.env` y los archivos de credenciales que coinciden con las reglas configuradas no son incluidos por Git.

## 5. Verificación reproducible

Desde la raíz del repositorio se pueden realizar nuevamente las comprobaciones mediante:

```bash
git check-ignore -v .env .env.local service-account-drive.json config/service-account-demo.json client_secret_demo.json credentials.json token.json private.pem private.key
python -m pytest -q tests/test_seguridad_secretos.py
```

Las pruebas comprueban que:

- los archivos sensibles quedan excluidos;
- `.env.example` puede versionarse;
- las variables sensibles se encuentran documentadas sin valores reales.

Estas verificaciones forman parte de la protección preventiva del repositorio.

Sin embargo, `.gitignore` y las pruebas de exclusión no sustituyen un escaneo del historial con una herramienta de detección de secretos.

## 6. Escaneo del repositorio con Gitleaks

Para comprobar que el historial actual del repositorio no contiene secretos detectables, se ejecutó:

```powershell
gitleaks git -v --redact
```

Gitleaks realizó correctamente el escaneo del repositorio.

En la ejecución final se obtuvo:

```text
34 commits scanned.
no leaks found
```

El resultado indica que Gitleaks no detectó secretos expuestos en el historial analizado.

La opción:

`--redact`

permite ocultar posibles valores sensibles en la salida de la herramienta.

## 7. Prueba positiva de Gitleaks

Obtener únicamente:

```text
no leaks found
```

no es suficiente para comprobar que Gitleaks funciona correctamente.

Por este motivo se realizó una prueba positiva controlada fuera del repositorio.

Se creó un directorio temporal utilizando PowerShell:

```powershell
$pruebaGitleaks = Join-Path $env:TEMP ("rn001-verificacion-" + [guid]::NewGuid().ToString("N"))

New-Item -ItemType Directory -Path $pruebaGitleaks | Out-Null
```

Dentro de este directorio se creó una configuración temporal de Gitleaks con una regla específica denominada:

`demo-secret`

También se generó un marcador sintético únicamente para la prueba.

El archivo de configuración y el archivo de prueba fueron creados utilizando codificación UTF-8 sin BOM.

Posteriormente se ejecutó Gitleaks sobre el directorio temporal:

```powershell
gitleaks dir "$pruebaGitleaks" --config "$rutaConfig" --max-target-megabytes 1 -v --redact
```

La herramienta detectó correctamente el patrón de prueba.

La salida mostró:

```text
Finding: REDACTED
Secret: REDACTED
RuleID: demo-secret

1 leaks found
Código de salida: 1
```

La prueba confirma que el resultado `no leaks found` obtenido en el repositorio no se debe a que Gitleaks esté fallando o deshabilitado.

Gitleaks sí detecta un secreto cuando existe un patrón válido.

El contenido utilizado para la prueba fue sintético y se generó fuera del repositorio.

Los valores detectados fueron mostrados como:

`REDACTED`

para evitar exponer información en la evidencia.

### Evidencia

`docs/sprint1/evidencias/RN-001_gitleaks_positiva.png`

### Resultado

**Cumple.**

La prueba positiva confirmó el funcionamiento del detector de secretos.

Las credenciales necesarias para las integraciones no deben almacenarse directamente dentro del código fuente.

Por este motivo se verificó la sección:

Se confirmó la existencia de los siguientes Repository Secrets:

- `GEMINI_API_KEY`

GitHub no muestra los valores reales almacenados en estos secretos, por lo que la evidencia únicamente permite visualizar sus nombres.

Esto evita exponer las credenciales dentro del repositorio y permite que los workflows o integraciones autorizadas puedan utilizarlas cuando corresponda.

## 11. Resultado final

RN-001 queda verificado correctamente con las evidencias disponibles.

La comprobación permitió confirmar que:

1. `.env` y otros archivos de credenciales se encuentran protegidos mediante `.gitignore`.
2. `.env.example` puede mantenerse dentro del repositorio sin contener valores sensibles.
3. Gitleaks puede ejecutarse correctamente sobre el historial del repositorio.
4. El escaneo actual no detectó secretos expuestos.
5. La prueba positiva controlada confirmó que Gitleaks sí identifica un secreto cuando existe un patrón válido.
6. Las credenciales de Gemini, LangSmith y Notion verificadas se encuentran configuradas mediante Repository Secrets en GitHub Actions.
7. Los valores reales de los secretos no aparecen en las evidencias generadas.

Por lo tanto, las verificaciones que anteriormente figuraban como pendientes cuentan actualmente con evidencia reproducible y pueden considerarse completadas.

## 12. Reglas de mantenimiento

Para conservar el cumplimiento de RN-001 durante las siguientes semanas se deben respetar las siguientes reglas:

1. No incluir tokens, contraseñas, claves privadas ni cadenas de conexión reales en código o documentación.
2. No eliminar las reglas de protección de `.gitignore` sin revisar previamente su impacto.
3. Mantener `.env.example` únicamente como plantilla y sin valores sensibles.
4. Utilizar Repository Secrets para las credenciales requeridas por GitHub Actions.
5. Ejecutar un detector de secretos antes de publicar cambios que involucren credenciales o configuración.
6. No mostrar secretos reales en capturas, logs o evidencias.
7. Si se detecta una credencial expuesta, revocarla o rotarla inmediatamente.
8. No asumir que eliminar un archivo del último commit elimina una credencial de todo el historial.
9. Revisar periódicamente que las reglas de exclusión continúen cubriendo los archivos de credenciales utilizados por las nuevas integraciones.

RN-001 queda cubierto específicamente por:

- reglas de exclusión;
- pruebas de `.gitignore`;
- escaneo de Gitleaks;
- prueba positiva de detección;
- configuración de Repository Secrets.

La asociación definitiva de CP-08 con su PBI correspondiente deberá mantenerse separada de RN-001.
