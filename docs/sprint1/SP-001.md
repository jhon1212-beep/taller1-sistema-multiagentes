# SP-001 — Spike técnico: LangGraph vs. CrewAI

**Fecha:** 30/09/2026  
**Sprint:** Sprint 1  
**Tipo:** Spike técnico  
**Objetivo:** Evaluar LangGraph y CrewAI para seleccionar el framework más adecuado para implementar agentes inteligentes orientados al seguimiento y supervisión de proyectos de software en entornos académicos.

---

## 1. Objetivo del Spike

El objetivo de este Spike fue investigar y probar alternativas para la construcción del sistema multiagente del proyecto.

Se compararon principalmente **LangGraph** y **CrewAI**, considerando cuatro criterios:

1. Integración con Python/FastAPI.
2. Trazabilidad mediante LangSmith.
3. Control del flujo y estado de los agentes.
4. Curva de aprendizaje.

Además de revisar la documentación oficial, se implementó una prueba de concepto (POC) con LangGraph utilizando Gemini como modelo de lenguaje. También se realizó una prueba adicional con CrewAI para comparar su implementación y comportamiento.

## 3. Comparación LangGraph vs. CrewAI

Se utilizó una escala de **1 a 5**, donde una puntuación mayor representa una mejor adecuación a las necesidades de esta POC.

En los criterios relacionados con complejidad y aprendizaje, una puntuación mayor representa una implementación más sencilla para el alcance evaluado.

| Criterio | LangGraph | CrewAI | Justificación |
|---|---:|---:|---|
| Integración con Python/FastAPI | 5/5 | 4/5 | Ambos frameworks trabajan con Python. LangGraph permitió implementar directamente la lógica mediante funciones, estado y nodos. La integración directa con FastAPI todavía no forma parte de esta POC. |
| Trazabilidad en LangSmith | 5/5 | 3/5 | La POC desarrollada con LangGraph permitió registrar y revisar la ejecución mediante LangSmith. En la prueba realizada con CrewAI no se habilitó una trazabilidad equivalente. |
| Control de flujo y estado | 5/5 | 3/5 | LangGraph permitió definir explícitamente el estado compartido, los nodos y las conexiones entre el agente GitHub simulado y el agente supervisor. |
| Curva de aprendizaje | 3/5 | 4/5 | CrewAI permitió definir rápidamente un agente mediante rol, objetivo y tarea. LangGraph requirió comprender previamente el manejo del estado y la construcción explícita del grafo. |
| **TOTAL** | **18/20** | **14/20** | |

Las puntuaciones corresponden a una evaluación técnica interna realizada para esta POC. Se sustentan en la documentación consultada y en las pruebas realizadas, por lo que no representan una medición universal de ambos frameworks.

## 6. POC con LangGraph

Se desarrolló una prueba de concepto utilizando LangGraph y Gemini.

El objetivo fue comprobar que era posible construir un flujo sencillo compuesto por dos nodos que compartieran información mediante el estado del grafo.

El flujo implementado fue:

`START -> agente_github -> agente_supervisor -> END`

### 6.1. Agente GitHub

El primer nodo fue denominado:

`agente_github`

Para esta POC, el agente GitHub fue simulado. En lugar de conectarse todavía a la API REST de GitHub, devuelve dos commits de prueba con los autores seudonimizados.

Los datos utilizados fueron:

- Integrante 1 — 28/09/2026 — estructura del repositorio.
- Integrante 2 — 29/09/2026 — modelo de datos inicial.

Esta simulación permite comprobar el flujo sin depender todavía de la integración definitiva con GitHub.

### 6.2. Agente Supervisor

El segundo nodo fue denominado:

`agente_supervisor`

Este nodo recibe mediante el estado de LangGraph los commits generados por el nodo anterior.

Posteriormente utiliza Gemini para generar un resumen neutral del avance del proyecto.

La instrucción utilizada solicita resumir el avance en dos frases y evitar realizar juicios sobre los integrantes.

## 10. Cálculo de viabilidad para 100 alertas diarias

Como escenario de referencia se consideran **100 alertas por día**.

Para realizar un cálculo inicial se supone que cada alerta requiere una llamada independiente a Gemini.

Por lo tanto:

`100 alertas × 1 solicitud = 100 solicitudes/día`

El límite gratuito observado para `gemini-3.8-flash` es:

`20 solicitudes/día`

Por lo tanto:

`100 / 20 = 5`

Esto significa que las 100 alertas requerirían **cinco veces la capacidad diaria disponible** si cada alerta se procesa mediante una llamada independiente.

En consecuencia, **100 alertas individuales por día no caben dentro del límite gratuito observado de 20 RPD**.

Para mantener el funcionamiento dentro del nivel gratuito sería necesario reducir la cantidad de llamadas al modelo.

Una alternativa para etapas posteriores sería agrupar varias alertas dentro de una misma solicitud o utilizar procesamiento por lotes, considerando también los límites de:

- 5 solicitudes por minuto (RPM).
- Aproximadamente 250 000 tokens de entrada por minuto (TPM).
- 20 solicitudes por día (RPD).

## 13. Decisión técnica

Después de realizar la investigación y las pruebas prácticas, se seleccionó **LangGraph** como framework para continuar con el prototipo.

La decisión se sustenta en los siguientes puntos:

1. Permitió definir explícitamente los nodos del flujo.
2. Permitió mantener un estado compartido entre los agentes.
3. Permitió controlar directamente el orden de ejecución.
4. Permitió integrar Gemini con el agente supervisor.
5. Permitió registrar y revisar la ejecución mediante LangSmith.
6. La estructura obtenida resulta adecuada para continuar incorporando nuevos agentes al prototipo.

CrewAI también logró completar la tarea y presentó una forma directa de trabajar mediante roles, objetivos y tareas.

Sin embargo, para las necesidades evaluadas en este Spike se priorizó el control explícito del flujo y del estado proporcionado por LangGraph.

El modelo seleccionado para la POC fue:

`gemini-3.8-flash`

## 15. Conclusión

El Spike permitió investigar y probar de manera práctica dos alternativas para la implementación del sistema multiagente.

La POC principal demostró que LangGraph puede organizar un flujo compuesto por dos nodos, transferir información mediante un estado compartido, utilizar Gemini para generar un resumen y registrar la ejecución mediante LangSmith.

La prueba adicional con CrewAI permitió comprobar que este framework también puede ejecutar la tarea planteada, aunque durante la prueba se presentaron errores temporales de disponibilidad del modelo.

Para el prototipo se seleccionó **LangGraph** y se utilizó **Gemini 3.8 Flash** como modelo.

Finalmente, el análisis de los límites gratuitos mostró que un escenario de 100 alertas independientes por día no cabe dentro del límite observado de 20 solicitudes diarias. Este resultado deberá considerarse posteriormente al diseñar la estrategia de procesamiento de alertas.
