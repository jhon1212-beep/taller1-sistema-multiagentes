# AR-04: contrato del módulo autenticacion

Responsable: Castro.  
Semana planificada: 6.  
Fecha real de implementación: 13/10/2026.  
Estado: implementado y probado; pendiente de revisión.

## Objetivo

Publicar el contrato del módulo `autenticacion` (dominio, puerto y adaptador
falso) para que `proyectos`, el frontend y las pruebas E2E programen contra
él sin esperar la autenticación real. Antes de AR-04 la carpeta solo tenía
un README.

## Desarrollo

Se siguió el mismo patrón de AR-01 (`evidencias`), AR-02 (`supervision`) y
`proyectos` (HU-002), definido en `docs/arquitectura.md` §3.

1. **Revisión de contexto.** Se leyeron el modelo `Docente` de
   `modelos_orm.py` (id, nombre, correo, password_hash, activo), el patrón de
   `proyectos/dominio.py` y `puertos.py`, y los docentes demo del frontend
   (`frontend/src/datos/demo.js`: `docente1..5@demo.test`).
2. **`dominio.py`.** Dataclasses `Docente` y `Sesion`, y dos excepciones:
   `CredencialesInvalidas` y `SesionInvalida`. `Docente` no lleva el hash de
   la contraseña: ese dato queda dentro del adaptador.
3. **`puertos.py`.** Protocol `ServicioAutenticacion` con tres operaciones:
   `iniciar_sesion(correo, password) -> Sesion`,
   `obtener_docente(token) -> Docente` y `cerrar_sesion(token)`.
4. **`adaptadores/falso.py`.** `ServicioAutenticacionFalso`, en memoria:
   - los 5 docentes demo con la clave demo del frontend;
   - contraseñas guardadas como PBKDF2 con sal y comparadas con
     `hmac.compare_digest`; solo biblioteca estándar, sin dependencias nuevas;
   - tokens con `secrets.token_urlsafe(32)`;
   - reloj inyectable y duración configurable (8 h por defecto) para probar
     la expiración sin esperar;
   - el correo se normaliza (espacios y mayúsculas).
5. **Pruebas** en `tests/unit/test_autenticacion_contrato.py`.
6. **README del módulo** actualizado con la tabla de archivos.

## Decisiones

- **Un solo error para credenciales.** Correo inexistente, clave errónea y
  docente inactivo lanzan `CredencialesInvalidas`; la respuesta no revela si
  el correo existe. El hash se calcula siempre, para no filtrarlo por tiempo.
- **Contrato sin tecnología.** El dominio no importa bcrypt, JWT ni FastAPI;
  el adaptador real puede elegir token opaco o JWT sin cambiar a quien lo usa.
- **Integración con `proyectos`.** Quien llame a `proyectos` obtiene el
  `docente_id` con `obtener_docente(token).id`; así se cumple HU-001
  (cada docente ve solo sus proyectos).

## Verificación

Desde la raíz:

```powershell
python -m pytest tests/unit/test_autenticacion_contrato.py -q
```

Las pruebas verifican: login correcto, normalización del correo, tres casos
de credenciales inválidas, docente inactivo, token desconocido, cierre de
sesión idempotente, expiración y unicidad de tokens.

Suite completa (`tests/unit`, `tests/integration`, `backend/tests`):
`47 passed`.

## Limitaciones

- No hay adaptador real (bcrypt + tabla `docente`) ni rutas HTTP de login.
- Las sesiones viven en memoria: se pierden al reiniciar y no se comparten
  entre procesos.
- No hay límite de intentos fallidos.
- Los tests `tests/test_health.py`, `test_modelo_datos.py` y
  `test_proyectos.py` no se pudieron ejecutar en este entorno por falta de
  `sqlalchemy` instalado; no están relacionados con este cambio.
