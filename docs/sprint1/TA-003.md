Registrar commit, fecha, ejecutor, entorno, datos de entrada, resultado obtenido y enlace a evidencia por cada ejecución.

Estados: **No ejecutado**, **Aprobado**, **Fallido** o **Bloqueado**. Solo aprobar cuando se cumplan todos los resultados esperados; indicar por separado las comprobaciones parciales. Registrar un defecto con pasos de reproducción si falla una funcionalidad disponible, y una dependencia si la funcionalidad no está implementada.

## Casos de prueba

### CP-01 · Conexión con GitHub y lectura de actividad — HU-001 — Alta

- **Precondición/datos:** repositorio de prueba accesible con al menos un commit, un PR y un issue; token válido cuando sea necesario.
- **Pasos:** ejecutar `python scripts/sync_github.py --config equipos.ejemplo.json`; revisar los JSON por equipo en `data/`; comparar con la actividad del repositorio y, cuando esté conectada, con la vista GitHub del equipo.
- **Esperado:** commits, PRs e issues con autor y fecha, asociados y persistidos para el equipo correcto. No aceptar listas vacías como evidencia de lectura de esos tres tipos.
- **Evidencia:** conteos, muestra anonimizada y archivo persistido. La prueba con una API simulada no acredita conectividad real.

### CP-02 · Límite de API de GitHub — HU-001 — Alta

- **Precondición/datos:** sincronización previa persistida; respuesta HTTP 403/429 con `X-RateLimit-Remaining: 0` y fecha de restablecimiento. Simular el límite sin agotar una cuenta real.
- **Pasos:** inyectar el error; sincronizar; comparar todos los datos previos, revisar incidencias y comprobar que otro equipo sigue procesándose; verificar posteriormente la ejecución del reintento programado.
- **Esperado:** conserva evidencia, métricas y fecha de última sincronización; marca fuente degradada, registra incidencia y reprograma el reintento.
- **Cobertura actual:** `tests/test_github_resiliencia.py` comprueba conversión del error HTTP, conservación y continuidad. El código registra `reintento_en_segundos`, pero no programa una ejecución futura: aceptación completa pendiente de ese mecanismo. Las variantes 404/red complementan, pero no sustituyen, el escenario de límite.

### CP-03 · Gestor de tareas Notion — HU-002 — Alta

- **Precondición/datos:** base autorizada con una tarea completa, una sin responsable, una sin fecha y otra sin ambos campos.
- **Pasos:** sincronizar, abrir Backlog y contrastar cada tarea con su registro de origen.
- **Esperado:** conserva responsable, estado y fecha; identifica expresamente campos faltantes sin omitir la tarea ni detener la sincronización.
- **Evidencia/dependencia:** salida del agente y vista conectada. La verificación de acceso de EN-002 es una precondición; no sustituye al agente de HU-002 ni a este caso completo.

### CP-04 · Documentación Google Drive — HU-003 — Media

- **Precondición/datos:** carpeta autorizada y lista de entregables esperados; un documento vigente, otro anterior al umbral de vigencia acordado y un entregable ausente.
- **Pasos:** registrar el umbral usado, sincronizar y consultar Documentación.
- **Esperado:** identifica cada entregable como existente, faltante o desactualizado, con fecha de modificación y vínculo al documento cuando exista.
- **Evidencia/dependencia:** salida del conector y comparación con la carpeta. Bloqueado mientras falte la integración funcional.

### CP-05 · Consolidación por equipo y semana — HU-004 — Alta

- **Precondición/datos:** GitHub, Notion y Drive sincronizados para dos equipos y dos semanas; registrar zona horaria y límites semanales utilizados.
- **Pasos:** consultar el resumen de cada equipo/semana mediante la API consolidada; repetir la sincronización y la consulta.
- **Esperado:** una respuesta reúne las tres fuentes, sin mezclar equipos o semanas ni duplicar evidencias al repetir la sincronización.
- **Evidencia/dependencia:** solicitudes y respuestas anonimizadas. Bloqueado hasta disponer de las tres fuentes y la API consolidada.

### CP-06 · Cálculo de avance y pendientes — HU-005 — Alta

- **Precondición/datos:** cuatro tareas del equipo, una terminada y tres pendientes; criterio de avance por cantidad de tareas acordado para este conjunto.
- **Pasos:** sincronizar y consultar el panel; terminar una segunda tarea, volver a sincronizar y consultar.
- **Esperado:** pasa de 25 % y tres pendientes a 50 % y dos pendientes; el panel refleja el recálculo. Si HU-005 define ponderaciones, ajustar los datos y el resultado esperado antes de ejecutar.
- **Evidencia/dependencia:** datos de entrada y valores antes/después. Las pruebas existentes de Gini, autores y días con commits son auxiliares: no prueban avance ni pendientes de tareas. Este caso requiere el flujo de tareas consolidado.

### CP-07 · Retrasos y semáforo de riesgo — HU-006 — Alta

- **Precondición/datos:** umbrales aprobados y registrados; equipos con valores por debajo, en el límite y por encima de cada umbral.
- **Pasos:** ejecutar el análisis y consultar Panel y Alertas; contrastar con la regla y sus límites inclusivos/exclusivos.
- **Esperado:** clasificación verde/amarillo/rojo coherente con los umbrales; cada alerta incluye causa y evidencia verificable.
- **Evidencia/dependencia:** regla usada, valores y salida del analizador. Bloqueado mientras solo exista la maqueta o falten reglas aprobadas.

### CP-08 · Roles y aislamiento — PBI por confirmar — Alta

- **Precondición/datos:** docente autorizado y dos estudiantes de equipos distintos, con autenticación funcional.
- **Pasos:** consultar como docente; consultar como estudiante su equipo; intentar consultar el otro equipo modificando el identificador en la solicitud; repetir sin sesión.
- **Esperado:** docente accede a sus equipos autorizados; estudiante solo al propio; acceso cruzado o anónimo rechazado por el servidor sin devolver datos ajenos.
- **Evidencia/dependencia:** respuestas HTTP sin tokens. Cambiar de rol en el prototipo no valida autorización; bloqueado hasta implementar autenticación y control de acceso.
